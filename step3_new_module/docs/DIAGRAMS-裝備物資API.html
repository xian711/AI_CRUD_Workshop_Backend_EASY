② 資料表 ER 圖：一筆品項怎麼存

只有一張主表 equipment_item（欄名 snake_case）。id 由 SEQUENCE 取號；code 有唯一索引；分類字典是程式常數，不建表、沒有外鍵（虛線）。選填欄存 null。

③ 循序圖：POST 新增＋編碼在交易內產生

先過驗證；有錯直接回 400，不進 Service。通過後在同一個交易裡：先取 id、再查同前綴最大流水號 +1 算出 code、寫入、提交。唯一索引 ux_equipment_item_code 是最後防線：真的撞號會丟例外、回 500，不會靜默重號。

%%{init: {'theme':'neutral','fontSize':22,'themeVariables':{'fontSize':'22px'},'sequence':{'actorFontSize':22,'messageFontSize':22,'noteFontSize':22,'width':260}}}%%
sequenceDiagram
  actor U as 前端／Swagger
  participant V as 框架驗證（DTO 規則）
  participant C as EquipmentItemsController
  participant S as EquipmentService
  participant DB as PostgreSQL

  U->>V: POST /api/equipment/items（發電機，JSON camelCase）
  V->>V: 必填、qty 大於等於 0、分類與狀態允許值、電話格式、日期不晚於今天
  alt 驗證失敗
    V-->>U: 400，errors 鍵 camelCase、繁中訊息（例：qty「數量不可小於 0」）
  else 驗證通過
    V->>C: Create(request)
    C->>S: Create(request)
    S->>DB: BEGIN 交易
    S->>DB: SELECT nextval('equipment_item_seq')
    DB-->>S: 25 → id = E-025
    S->>DB: 查前綴 PW-GEN- 的現有 code
    DB-->>S: PW-GEN-001、PW-GEN-002 → 最大流水 2
    S->>S: code = PW-GEN-003；updatedAt = 今天（本地時區）
    S->>DB: INSERT equipment_item
    S->>DB: COMMIT
    Note over S,DB: 唯一索引是最後防線（撞號 → 500）
    S-->>C: ModelResult { success: true, data }
    C-->>U: 201 Created ＋ Location: /api/equipment/items/E-025
  end

④ 狀態碼矩陣：五條路由會回什麼

一列一條路由，右邊是它會回的狀態碼。綠色＝成功，橘色＝預期的失敗，紅色＝未預期例外。除了 DELETE 成功的 204，成功和 404 都包成 ModelResult（{ success, message, data }）；400 是框架的驗證格式，errors 的鍵是 camelCase、訊息是繁中；409 契約保留，本版不發出（虛線框）。
