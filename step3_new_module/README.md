# Step 3｜複製範本開發新模組（後端）

> **這一步你不寫程式，你當的是「提需求、做決策、驗成果」的人。**

前面兩步你已經玩過範本 API（人員 CRUD，.NET＋PostgreSQL，跑在 port 5080）、看過 harness（`CLAUDE.md`、`CODE-RULES-api-本專案.md`、`contract-conventions-summary.md`、`使用說明-複製範本開發新API模組.md`，外加給 Codex 用的 `AGENTS.md`）、認識了分層架構與資料庫綱要。這一步要用同一套範本＋harness，長出一個全新模組的後端：**中心裝備物資**——把上一堂前端課做出來的假資料（F5 就消失），接上真的 API 與 PostgreSQL 資料表。

你要做的只有三件事：讀懂需求（3.1）、把需求丟給 AI 並拍板範圍（3.2）、打開 swagger／psql 驗收與修正（3.3）。寫程式的粗活是 AI 的事。

---

## 3.0 準備工作區

動手之前，先把範本 API 複製成你自己的工作專案，並確認 AI Agent 的工作目錄就是這個專案根目錄（不然 AI 讀不到題目文件與 harness 規則）。完整指令在 [`PROMPTS.md`](PROMPTS.md) 的 **3.0 準備工作區指令**，重點三步：

1. 複製 `step2_speedrun_kit\2.5_sample_api\sample-api` → `step3_new_module\my-equipment-api`（harness 四件在範本根目錄，會一起帶走）。
2. 只把 `PRD-中心裝備物資-後端.md` 複製進工作專案（AI 才讀得到需求）。
3. 進 `my-equipment-api` 資料夾，在這裡開 AI Agent。

> **範圍答案（SCOPE）由講師在你完成釐清問答後才發放，先別偷看。** 這一步的重點就是你親自跟 AI 把範圍釐清出來；答案先進工作區＝直接抄，練習就沒了。所以工作區「只放 PRD、不放 solution-api、不放 instructor」。

> 範本根目錄已自帶 harness 四件（`CLAUDE.md`、`CODE-RULES-api-本專案.md`、`contract-conventions-summary.md`、`使用說明-複製範本開發新API模組.md`）＋給 Codex 用的 `AGENTS.md`。複製走範本，harness 就跟著走——AI 一進來就讀得到全套規則。

---

## 3.1 讀 PRD

打開 [`PRD-中心裝備物資-後端.md`](PRD-中心裝備物資-後端.md)，先讀懂「這個後端要服從什麼契約、哪裡刻意留白」。

### 這份 PRD 跟前端課的 PRD 差在哪？

| 前端課 PRD | 這份後端 PRD |
|---|---|
| 從**真實系統原始碼**逆向整理 | 從**前端課成品**逆向整理 |
| 決定「畫面要長什麼樣、欄位做幾個」 | 契約已被前端凍結，決定「資料怎麼落地、編碼怎麼產」 |
| 留白在「做不做某個功能」 | 留白在「同一件事怎麼實作」（編碼誰產、刪除策略、分頁在哪做…） |

### 讀 PRD 時要抓的三個重點

| 重點 | 在哪 | 為什麼重要 |
|---|---|---|
| **契約欄位表（13 欄）** | 第 3 節 | 欄名是前端定死的，後端一個都不能改；必／選填有明確證據（前端 `[id].vue` 的驗證規則） |
| **編碼規則** | 第 4 節 | `IT-LAP-001` 三段怎麼組、字典從哪來、流水號怎麼數，都要照前端那份 |
| **刻意留白的 6 個釐清點** | 第 5 節 | 這正是 3.2 要你跟 AI 敲定的東西——PRD 不給答案 |

> **心法：後端不是重新發明需求，是「服從前端已經定好的契約」＋「把留白的實作決策敲定」。** 看到留白不要慌，那是設計好的岔路，交給 3.2 處理。

## 3.2 把需求丟給 AI，讓它先問問題

你不會叫 AI「照 PRD 做」就走開——PRD 第 5 節那些留白它自己亂決定，你就失去把關的機會。正確流程是**先釐清、再動工**：

### 生成流程圖

```
你：貼【起手 prompt】（PROMPTS.md 有現成的，直接複製）
        │
        ▼
AI：依序讀 CLAUDE.md → AGENTS.md → CODE-RULES-api-本專案.md → contract-conventions-summary.md → PRD
        │
        ▼
AI：先不寫程式，改用「選擇題」問你 5-7 題範圍釐清（每題附選項與建議）
        │
        ▼
你：一題一題拍板（可直接採納建議選項）
        │
        ▼
AI：輸出 SRS-delta／SDD-delta 與任務清單，停下來等你確認
        │
        ▼
你：確認開工
        │
        ▼
AI：照分層順序逐任務開發（Entity→migration→DTO→Mapper→Service→Controller→seed→測試），每完成一個回報一行
```

用一句話記：**貼 prompt → AI 問 → 你答 → AI 出 delta＋任務清單 → 你確認 → AI 逐項做並回報。**

### 為什麼要讓 AI 先問問題？

因為 PRD 第 5 節有六條「做得出來、但怎麼做要人決定」的岔路：編碼誰產生、id 怎麼產、分類字典要不要建表、刪除硬刪還是軟刪、分頁在哪做、日期可不可空。AI 先用選擇題把岔路攤開來，你拍板，範圍與實作方向才會定下來。這跟 spec-kit 的 clarify 是同一個道理：**先問對問題，再寫對程式。**

> **別把「AI 有先問選擇題」當成 harness 的效果。** AI 先問＝起手 prompt 的 workflow 指令被遵守（我們在 prompt 裡明寫「先問我」）。harness（規則＋範本）的效果體現在**生成的程式碼品質**——分層乾淨、命名一致、驗證到位、封裝格式統一、測試不放水。兩者是不同層次的東西。

實際會問哪幾題、課堂怎麼裁決，完整六題與理由**只在** [`SCOPE-後端課堂範圍決策.md`（講師版）](../instructor/SCOPE-後端課堂範圍決策.md)，由講師在你完成釐清問答並說出理由後才發放。這裡先列出六個待你自己釐清的問題面向——**不列建議選項、不列裁決**，你要跟 AI 討論、拍板，再把理由填下來：

| # | 待釐清的問題面向 | 你的裁決 | 你的理由 |
|---|---|---|---|
| Q1 | 品項編碼 `code` 誰產生？ |  |  |
| Q2 | `id`（E-001）怎麼產？ |  |  |
| Q3 | 分類字典要不要建表？ |  |  |
| Q4 | 刪除策略？ |  |  |
| Q5 | 分頁／篩選／排序在哪做？ |  |  |
| Q6 | `purchaseDate` 可否為空？ |  |  |

> 這六題不用背。重點是理解：**每一題都是在「一種慣例」和「這堂課的需求」之間做取捨**，而做取捨的人是你，不是 AI。先自己跟 AI 討論、拍板，把理由寫下來——課後對照講師發的答案，比對自己的裁決哪裡想的一樣、哪裡不一樣。

如果 AI 沒問就直接開始寫程式，別讓它跑——救援與各種歪樓的回法見 [`PROMPTS.md`](PROMPTS.md) 的【常見歪樓對照表】。

## 3.3 察看結果，反覆修正

AI 逐任務做完後，換你上場驗收。**三路驗收，缺一不可**：

### 三路驗收

| 路 | 怎麼驗 | 期望 |
|---|---|---|
| **swagger** | 開 `http://localhost:5080/swagger`，五條路由各打一次 | GET 全量 24 筆、GET 單筆／404、POST 201＋Location、PUT 200／404、DELETE 204／404 |
| **測試** | 在 `my-equipment-api` 跑 `dotnet test` | 全綠；測試數以 `docs/TASKS.md` 為準 |

> **想看參考解生出來的 delta 文件長什麼樣？** 在本資料夾的 `docs/`：
> [`SRS-裝備物資API-delta.md`](docs/SRS-裝備物資API-delta.md)（需求差異：新資源、欄位表、行為規則）、
> [`SDD-裝備物資API-delta.md`](docs/SDD-裝備物資API-delta.md)（設計差異：狀態碼矩陣、資料表綱要、編碼取號）、
> [`TASKS.md`](docs/TASKS.md)（任務清單）。
> **建議你自己先生一份再打開對照**——直接抄等於跳過這一步最重要的練習。
> 這三份也是講師 checkpoint 會複製進學員專案的文件。
| **psql** | 用絕對路徑連 `ai_crud_equipment`，`SELECT count(*) FROM equipment_item` | 24 列，`code` 與前端種子一致 |

現成的收工檢查指令（含 psql 絕對路徑寫法）在 [`PROMPTS.md`](PROMPTS.md) 的【收工檢查 prompt】。

> **psql 這一路最關鍵。** swagger 有回資料不代表資料真的存進去了——只有 psql 在資料庫裡查得到 24 列，才證明「持久化」真的成立。這正是這堂課跟前端課最大的差別：前端課 F5 就消失，這堂課關機再開資料還在。

### 修正心法（三條）

| 心法 | 怎麼做 | 為什麼 |
|---|---|---|
| **一次只修一個問題** | 一則訊息只提一件事，改完再看下一件 | 一次丟五個問題，AI 顧此失彼，你也分不清哪個改動造成哪個結果 |
| **描述「看到什麼 vs 期望什麼」** | 「POST 回的 code 是空字串，我期望是 IT-LAP-003」 | 給 AI 具體落差，它才知道改哪、改成什麼；只說「不對」它只能猜 |
| **兩次修不好就重新描述** | 換個說法把問題重講一次，別在同一串繼續盧 | 同一句反覆盧，AI 會越改越歪；重新描述等於給它乾淨的起點 |

修正 prompt 的現成句型見 [`PROMPTS.md`](PROMPTS.md) 的【修正 prompt 範本】。

## 產出物清單

AI 跑完這一輪，會交出三類東西：

| 產出 | 是什麼 | 你要看什麼 |
|---|---|---|
| **SRS-delta／SDD-delta**（在 `docs/`） | 只記「與人員範本的差異」，含分頁前端做、資料量假設等限制 | 對照你的六題裁決有沒有漏、有沒有多；範本正本沒被動到 |
| **程式碼（一整套裝備模組）** | Entity→migration→DTO→Mapper→Service→Controller，加唯一索引與 seed | 分層有沒有照範本、`code`／`id` 有沒有後端產生 |
| **測試** | 單元＋整合測試 | 全綠、沒有被刪或放寬；測試數以 `docs/TASKS.md` 為準 |

> `docs/` 與 `solution-api/`（參考解）由課程備妥，**先自己做，真的卡住兩次以上再去看**——直接抄答案學不到「怎麼跟 AI 提需求、怎麼三路驗收」，那才是這堂課的重點。

## 卡住怎麼辦？

- AI 沒問就動工、想自建分類表、想改 SDD 正本、測試紅了想刪測試——回法都在 [`PROMPTS.md`](PROMPTS.md) 的【常見歪樓對照表】。
- 環境類故障（5432 沒開、5080 被占、migration 失敗）——由講師處理，分流見講師手冊。
- 生成落後太多——講師會在約第 85 分鐘視情況套參考解讓大家跟上驗收。
