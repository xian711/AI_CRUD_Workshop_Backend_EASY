# 後端課堂範圍決策 — 中心裝備物資（持久化）

> **講師版答案**：學員完成釐清問答並說出理由後才發放；**勿放進學員工作區**（`step3_new_module\my-equipment-api\`）。

> 真實契約見 [PRD-中心裝備物資-後端.md](../step3_new_module/PRD-中心裝備物資-後端.md)（第 5 節列了六個刻意留白的釐清點）。
> 本文件＝那六題釐清選擇題的**參考答案**，也是 `solution-api/` 實作的依據。

## 為什麼要先釐清？

這份 PRD 的契約（欄位、編碼規則）是前端凍結的，不可改；但**怎麼把它落地到後端**，PRD 刻意不給答案。直接叫 AI「照 PRD 做」，它會自己亂決定編碼誰產、要不要建字典表、硬刪還軟刪——你就失去把關的機會。**先問對問題，實作方向才會定下來。**

這六題每一題都是在「一種現成慣例」和「這堂課的實際需求」之間做取捨。特別是 Q1，答案**刻意偏離範本的做法**——這是全課最重要的教學點：慣例不是教條，遇到不同需求要敢偏離，並把理由記下來。

## 釐清選擇題與裁決（六題，逐題）

### Q1. 品項編碼 `code`（如 `IT-LAP-001`）由誰產生、怎麼保證不重複？

- 選項：(a) 前端算好傳給後端 (b) **後端產生，前端只做預覽** (c) 資料庫 trigger 產生
- **課堂裁決：(b) 後端產生。** 同前綴取現有最大流水號 +1，在**同一個交易**內完成；`code` 欄加唯一索引 `ux_equipment_item_code`。
- **白話理由**：前端那個編碼預覽只是給使用者看的即時提示，真正入庫時，唯一性只有資料庫端能保證。兩個人同時新增同前綴的品項，若讓前端各自算，就會撞號；後端在交易裡算 +1、再靠唯一索引兜底，才不會產生重複編碼。
- **教學點（本課最重要）**：範本的 D6 是用單一 `SEQUENCE` 產流水號。但這裡的流水號是「**每個前綴各自從 001 數**」（`IT-LAP-` 一組、`PW-GEN-` 另一組），單一 SEQUENCE 做不到分組計數——**所以要敢偏離範本慣例**，改成「查同前綴 MAX+1」，並把「為什麼偏離、偏離成什麼」寫進設計文件-delta（DESIGN）。這就是「同一套慣例、不同需求要敢偏離並記錄」的示範。學員若照抄範本 SEQUENCE 硬套，會做不出分組流水號——引導他們發現這個落差。

### Q2. `id`（如 `E-001`）怎麼產？

- 選項：(a) **沿用範本 SEQUENCE 機制** (b) 自己另想一套 (c) 用 GUID
- **課堂裁決：(a) 沿用範本 D6。** 建 SEQUENCE `equipment_item_seq` 起始 25，格式 `E-###`；種子 24 筆用**顯式 id**（E-001~E-024），seed 完把 SEQUENCE `RESTART 25`，之後新增從 E-025 接上。
- **白話理由**：id 只需要「全表唯一、遞增」，沒有分組需求，範本的 SEQUENCE 剛好合用——**能沿用就沿用，不必為了不同而不同**。這跟 Q1 剛好對照：Q1 因為需求不同要偏離，Q2 因為需求相同要沿用。
- **教學點**：讓學員體會「偏離範本」不是預設動作，而是**需求逼你偏離時才偏離**。同一支程式裡，id 沿用、code 偏離，兩個決策並存且各有理由——這才是成熟的工程判斷。種子顯式 id 與 SEQUENCE 起始值的銜接（RESTART 25）是常見坑，要提醒。

### Q3. 分類／項目字典要不要建資料表？

- 選項：(a) 建 `equipment_category` 表＋外鍵 (b) **不建表，用程式常數驗證**
- **課堂裁決：(b) 不建表。** 後端以常數清單驗證 `categoryKey ∈ 10 類；類別碼字典與 `ITEM_CODE_MAP`（項目碼）兩份字典搬到後端常數檔（產編碼用，查無項目碼→`OTH`）。`name` **不驗證**是否屬於該分類的標準項目（OTHER 分類可自填品名）。
- **白話理由**：字典建表更「正規」，但這堂課只有一張主表就夠教 CRUD 全鏈路了；再拉一張字典表＋外鍵，複雜度暴增卻沒教到新東西。字典內容穩定、量小，當常數就好。`name` 不綁字典是刻意的取捨——OTHER 分類要能自填、字典日後演進也不想動後端。
- **教學點**：「正規化」不是越多越好；課堂範圍要的是**小而完整**。把「不驗 name 屬不屬於標準項目」這個取捨明白記進設計文件-delta，示範「知道自己少做了什麼、並說得出為什麼」。

### Q4. 刪除是硬刪還是軟刪？

- 選項：(a) **硬刪除**（DELETE 真的刪一列） (b) 軟刪除（改狀態旗標）
- **課堂裁決：(a) 硬刪除。** DELETE 成功回 204、不存在回 404——與前端課的裁決、範本 D5/D9 一致。
- **白話理由**：硬刪最直觀，CRUD 的 D 要教得乾淨；而且前端課已經定案硬刪，後端要跟前端契約一致。軟刪是正式環境常見做法，但會多一個 `is_deleted` 旗標與到處要加的過濾條件，屬第二階段。
- **教學點**：跨層一致性——後端的刪除語意要跟前端、跟契約對齊，不能各做各的。正式環境建議軟刪，這點記進設計文件-delta 待辦即可。

### Q5. 分頁／篩選／排序在後端做還是前端做？

- 選項：(a) 後端分頁（API 收 page/size 參數） (b) **前端做，API 回全量**
- **課堂裁決：(b) 前端做。** API `GET` 回全部資料，分頁／篩選／排序由前端處理；此決策的前提「資料量 < 1000 筆」要寫進設計文件-delta 的限制段。
- **白話理由**：課堂資料才 24 筆、正式情境也預估 < 1000 筆，全量回傳前端跑得很順；後端分頁要多設計參數、多寫測試，這堂課的重點是 CRUD 骨架，不是效能。但**這是有前提的決策**，前提要寫下來——資料量一大就得回頭改後端分頁。
- **教學點**：技術決策要連「前提」一起記。「前端分頁」不是永遠對，是「在 < 1000 筆前提下對」。把假設寫進設計文件-delta，日後量變大時才知道要回來改哪裡。

### Q6. `purchaseDate` 可不可以是空的？資料庫怎麼存？

- 選項：(a) 必填、不可空 (b) **可空，存 null**
- **課堂裁決：(b) 可空。** `purchaseDate` 用 `DateOnly?`（可為 null）；前端的空字串 ↔ null 由**前端 adapter 正規化**。選填欄共五個：`keeper`、`keeperPhone`、`locationName`、`purchaseDate`、`specNote`；必填六個：`categoryKey`、`name`、`qty`、`unit`、`spec1`、`status`（依前端 `[id].vue` 驗證規則）。`updatedAt` 比照範本 D12。
- **白話理由**：前端表單允許採購日期留空（`save()` 只在「有填且晚於今天」才報錯），後端就得能存空值。空字串進資料庫當日期會出錯，所以存 null，型別用可空的 `DateOnly?`；空字串 ↔ null 的轉換放前端 adapter，後端只認 null。
- **教學點**：必／選填不是用猜的，要回去讀前端的驗證規則當證據（`rulesFor()` 與 `save()`）。逐欄的 nullable／`[Required]`／CHECK 對照表放進設計文件-delta。

## 追加題（AI 照最小樣板「釐清規矩」會多問的）

題號接在 Q6 後面，順序依 AI 實際問的為準。以下是一定會碰到的兩類的參考答案。

### 追加 A. 保管人要存「人員編號」還是存「姓名、電話文字」？

- 選項：(a) **存姓名、電話文字**（`keeper`、`keeperPhone` 兩個文字欄） (b) 存人員編號（例如 `M-001`，外鍵連到範本的人員資料表，姓名電話從人員帶出） (c) 兩個都存（編號＋當下的姓名電話）
- **課堂裁決：(a) 存文字。**
- **白話理由**：前端契約已經定好 `keeper`、`keeperPhone` 兩個文字欄，前端畫面也是自己打字；PRD 說前端不改，選 (b)、(c) 都要多一欄、前端要改成「從人員清單挑」。保管人也可能是不在人員清冊裡的外部志工。
- **代價（要寫進 SRS-delta 第 4 段「待定與風險」）**：人員改名、換電話，裝備這邊不會跟著變；同名的兩個人分不出來。**正式系統建議改成 (b) 或 (c)**，前後端一起改。
- **教學點**：「存編號還是存文字」是資料庫設計最常見的岔路。存編號資料一致，存文字簡單、而且保留當時的樣子。沒有標準答案，要看契約和業務，並把代價寫下來。

### 追加 B. 數字和文字的上下限

- **課堂裁決**：數量 ≥ 0、不另設業務上限，但仍受整數型別限制（最大 2147483647）。2026-10-12 起教材前端也擋小數和超過整數上限。文字長度以參考解為準：名稱 50、單位 10、規格 200、保管人 50、保管人電話 20、存放地點 100、備註 500 字。
- **白話理由**：前端原本沒寫上限（2026-10-12 起已補上同一組數字），但資料表的文字欄要有長度；長度定在常見內容放得下、又擋得住亂貼一大段的程度。超過時回 400、訊息繁中。
- **前端已同步（2026-10-12）**：實拍 Step 4 LOOP 時子代理挑到「前端沒有字數上限、數量收小數、後端回 400 時整頁變錯誤頁」（手冊 Step 4 ⑥ Q2、⑧）。教材的 `step4_loop_e2e/fullchain-app` 已補上同一組字數上限、整數檢查，並接住 400 在欄位顯示紅字（見 `FULLCHAIN_NOTES.md`）。學員跑 LOOP 時多半不會再看到這題；看到了，依序核對：教材是不是舊版（`git pull`）、前端是不是從 `step4_loop_e2eullchain-app` 啟動、學員的 Q9 上限是不是跟這組數字不同、後端 400 的格式（`errors` 鍵是欄位名 camelCase）對不對。LOOP 中仍不改前端，先記入報告。

## 課堂版契約速查（凍結，`solution-api` 以此為準）

- 路由：`GET/POST /api/equipment/items`、`GET/PUT/DELETE /api/equipment/items/{id}`；行為同範本（201＋Location、404、204、400 錯誤鍵 camelCase、`ModelResult` 封裝、DELETE 無封裝）。
- `EquipmentItemResult`（camelCase）：id, code, categoryKey, name, qty, unit, spec1, keeper, keeperPhone, locationName, status, purchaseDate, specNote, updatedAt。
- `EquipmentItemRequest`：上述扣除 id / code / updatedAt。`status ∈ normal/maintenance/scrapped`（DB CHECK）；`qty` 為 int、≥ 0。
- DB：開發 `ai_crud_equipment`／測試 `ai_crud_equipment_test`；表 `equipment_item`（snake_case）；port 5080（一次只跑一支 API）。
- 種子 24 筆與前端 mock 逐欄一致（同 code、同內容）。

## 必／選填判定依據（給講師答疑用）

證據在前端 `pages/equipment/crud/[id].vue`：

- `rulesFor()`（約 349–358 行）設 `required: true` 的欄位＝ `categoryKey`、`name`、`unit`、`spec1`、`status`。
- `save()`（約 377–384 行）在引擎外檢查 `qty`（非數字或 < 0 報錯）→ 必填；`purchaseDate` 只在「有值且 > 今天」報錯，空值放行 → 選填。
- 其餘欄位無 `required` → 選填；`keeperPhone` 僅「填了才驗格式」。

歸納：必填 6（categoryKey/name/qty/unit/spec1/status）、選填 5（keeper/keeperPhone/locationName/purchaseDate/specNote）、系統產生 2（id/code）。
