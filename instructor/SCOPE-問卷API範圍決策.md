# SCOPE 六題裁決 — 問卷 API（step6 課後練習）

> **講師專用。學員版只出題不給答案**（見 `step6_survey_api/README.md` 第五節）。
> 這份的用途：對答學員的裁決品質。**重點不是他選了哪個，是他講不講得出理由。**

## 怎麼評

| 學員的回答 | 判定 |
|---|---|
| 選了任一選項，**講得出理由，理由跟 PRD 或既有契約有關** | ✅ 通過。選哪個都可以 |
| 選了「建議選項」，但講不出為什麼 | ❌ 沒通過。這叫抄答案，不叫裁決 |
| 沒裁決就開工，讓 AI 自己決定 | ❌ 沒通過。這正是 step1 第一項對照講的「決定是誰做的」 |

## Q1　`id` 怎麼產？

| 選項 | 說明 |
|---|---|
| A | 後端 SEQUENCE 產 `R-###`（前綴照前端已經在用的 `R-001`；取號方式照範本 `M-###`／裝備 `E-###` 的 SEQUENCE） |
| B | PostgreSQL `bigserial` 純數字自增 |
| C | UUID |

**建議：A。** 理由：前端課的 survey-app 已經在產 `R-001`（`R-` ＋ 3 碼），**格式以已經存在的那一端為準**；
取號方式則照範本 D6 用 SEQUENCE，取代前端「掃最大值 +1」的寫法（交易安全、無併發競態）。
前端型別 `id: string` 收得下。選 B 也可以，但要注意前端型別是 `string` 不是 `number`，
DTO 要轉字串——**這件事有沒有被學員講出來，是這一題最好的觀察點**。

> 學員如果照範本慣例自己換一個前綴（例如 `S-###`），不算錯，但要問他：
> 「前端現在的資料長 `R-001`，你換了前綴，有沒有寫進設計文件-delta？」——偏離可以，偏離要有記錄。

**要注意的陷阱**：問卷不像裝備有「分類前綴」，所以不需要裝備那種「每前綴各自計數」的偏離。
如果學員照抄裝備的 MAX+1 寫法，問他「這裡有幾種前綴？」——只有一種，SEQUENCE 就夠了，
抄了反而多做。**這是「照抄範本」與「照範本的精神」的分界。**

## Q2　`submittedAt` 誰產、什麼格式？

| 選項 | 說明 |
|---|---|
| A | 後端產，本地時區，格式 `YYYY-MM-DD HH:mm`（照 PRD 字面） |
| B | 後端產，存 `timestamptz`，回 ISO 8601，前端自己格式化 |
| C | 前端送上來，後端照收 |

**建議：A。** 理由：`CLAUDE.md` 的契約要點明講「`updatedAt` 後端本地時區寫入（禁 UtcNow / toISOString）」，
沿用同一慣例；而且前端型別是 `submittedAt: string` 且 PRD 寫死了格式，回 ISO 會讓前端要改——**違反這一關的核心要求**。

**C 是明確的錯誤答案**，理由要講清楚：時間戳讓前端送，等於讓填答者的電腦時鐘決定資料，
改個系統時間就能偽造送出時間。**「誰產」這件事的判準是「誰可信」，不是「誰方便」。**

> 選 B 的學員如果講得出「因為要跨時區、要能排序、要能做時間區間查詢」，也算通過——
> 但要追問：「那前端 `submittedAt: string` 的型別誰改？呼叫端會不會被迫改？」
> 這一追問正好帶到本關的驗收重點。

## Q3　單選題的值在資料庫怎麼存？

前提先講清楚：前端 composable 的型別是**中文字面量聯集**
（`'太簡單' | '剛好' | '太難'`、`'是' | '否'`……），API 進出只能是中文，這一點**不是選項**。
這一題問的是「資料庫裡存什麼」。

| 選項 | 說明 |
|---|---|
| A | 存中文原值（跟 API 同一份字面值），DTO `[AllowedValues]` 與 DB CHECK 共用一個常數檔，不建表 |
| B | 資料庫改存英文 key（`too-easy`／`just-right`／`too-hard`），Mapper 進出時中英轉換 |
| C | 建字典表 `survey_option`，存外鍵 |

**建議：A。** 理由：**契約以已經存在的那一端為準**——前端送的就是中文。
範本本身就是這樣做的：`MemberEnums.cs` 的性別「男／女」、狀態「在職／停用」都是中文，
DTO `[AllowedValues]` 與 CHECK constraint 共用同一份常數（`CODE-RULES-api-本專案.md`：PostgreSQL 一律 UTF-8，中文字面值不需 `N''` 前綴）。
欄位用 `text` 或 `varchar(n)`；`varchar(n)` 算的是字數，不是位元組。
要注意的細節：`'LOOP 驗證'`、`'寫 CODE-RULES'`、`'PRD 流程'`、`'為什麼要 harness'` 都含**半形空格**，少一格就會被 `[AllowedValues]` 擋下來。

**B 的問題**：多一層中英對照，兩份字面值要同步；換來的好處（改文案不動資料、多語系）PRD 都沒要求。
選 B 也可以通過，但要講得出理由，而且對照表必須寫進設計文件-delta。
**C 的問題**：這是 step3 Q5「字典要不要建表」的同一題。選項固定、不會被使用者維護，
建表是**過度設計**——這正是 harness 六條鐵律裡「範圍外預設移除」要擋的東西。

> **這一題的陷阱在 AI**：AI 很常「順手」把中文選項換成英文 key（`too-easy`），甚至把「是／否」做成 boolean。
> 後端自己看起來很漂亮，但前端送 `"剛好"` 進來就被 400 擋掉——呼叫端被迫改，正好違反這一關的核心要求。

> **這一題最容易出現「AI 自己就建了字典表」**。學員如果沒擋下來，
> 正好拿來複盤 step1 第三項：harness 管「怎麼寫」，管不了「做多少」。

## Q4　後端要不要重驗一次必填？

| 選項 | 說明 |
|---|---|
| A | 全部重驗（必填、允許值、字數上限） |
| B | 不驗，信任前端 |
| C | 只驗關鍵欄位 |

**建議：A。** 理由：**前端驗證是使用者體驗，後端驗證是資料完整性，兩者不是同一件事。**
API 一旦公開，任何人都能繞過前端直接打（用 curl、Postman、瀏覽器 console 都行）。
`CLAUDE.md` 第 3 條就寫了「DTO 驗證用 DataAnnotations ＋ IValidatableObject」，這是專案底線。

**B 是明確的錯誤答案。** 如果學員選 B，問他一句：
「你的 API 網址會出現在瀏覽器的 network 面板裡，我用 curl 直接打送一筆滿意度 999，會怎樣？」

**C 可以通過**，但要講得出「哪些是關鍵、為什麼」，而且不能漏掉「允許值」——
`rating` 若沒擋（例如送 999），統計就會被污染。

## Q5　「清空全部」與「匯出 CSV」誰做？

| 選項 | 說明 |
|---|---|
| A | 清空改成 `DELETE /api/survey`；匯出留前端 |
| B | 兩個都留前端 |
| C | 兩個都搬後端（後端出 CSV 檔） |

**建議：A。** 理由分兩半，要分開講：

- **清空必須搬後端**。資料現在在資料庫，前端清 `localStorage` 已經清不到任何東西了——
  **不搬就是壞掉**，不是設計選擇。
- **匯出不必搬**。BR-6 只要求「UTF-8 BOM ＋ 檔名含日期」，前端拿到 `GET /api/survey` 的
  JSON 自己組 CSV 就好。搬到後端要多一個端點、多一組測試、多一份格式規格，
  **換來的好處是零**——這就是過度設計。

**B 是明確的錯誤答案**（清空會失效）。
**C 可以通過**，但要講得出「為什麼值得多做一個端點」。多半講不出來，正好用來教「範圍怎麼收」。

> **順帶教一件事**：`DELETE /api/survey`（清空全部）是危險端點。
> PRD 第 6 節說管理頁不設密碼——那這個端點誰都能打。
> 學員如果自己想到這一點並在設計文件-delta（DESIGN）裡記下風險，**大加分**，那正是 Q6 要問的事。

## Q6　`GET /api/survey` 要不要保護與分頁？

| 選項 | 說明 |
|---|---|
| A | 全開、全量回傳，但在設計文件-delta 明寫這是教學簡化與其風險 |
| B | 全開但加分頁 |
| C | 加一把簡單的 key（header 或 query） |

**建議：A。** 理由：PRD 第 6 節「範圍外」明列「登入與權限」，加認證是**超出範圍**；
回覆筆數就是一班學員（幾十筆），分頁是**過早最佳化**。
**但一定要把風險寫進設計文件-delta**——這才是 A 跟「沒想過」的差別。

**這一題真正在考的不是選項，是「有沒有誠實揭露邊界」。**
對答時直接翻學員的 `docs/DESIGN-問卷API-delta.md`：

- 有沒有寫「本 API 無認證，回覆內容可被任何知道網址的人取得」？
- 有沒有寫「全量回傳，適用 <1000 筆假設；超過要改 server-side paging」？
- `DELETE /api/survey` 有沒有標「無認證的破壞性端點，正式環境必須加保護」？

**三條都有 → 滿分。** 一條都沒有 → 就算他選了「建議選項」也不算通過，
因為他只是猜對，沒有真的想過。

> 這一題直接呼應 `BUILD_LOG.md` 第 4 節「已知邊界」與 HANDBOOK step5 的「這門課沒教到什麼」。
> **能誠實講出自己做的東西哪裡不能上線，比做得完整更值錢。**

## 對答之後：接縫驗收

六題對完，最後看這一關真正的重點——**呼叫端有沒有被迫改**。

```powershell
powershell -ExecutionPolicy Bypass -File .\step6_survey_api\verify-seam.ps1
```

它先確認 `seam/useSurveyResponses.before.ts` 跟前端課 survey-app 的真檔逐字相同
（預設找跟後端課 repo 同一層的 `AI_CRUD_Workshop_Frontend_EASY`，可用 `-FrontendRepo` 指定；講師機器建議加 `-Strict`），
再比 before／after 的對外介面。

有學員自己前端專案的話，驗真的那兩版（第 1 關會自動略過）：

```powershell
.\step6_survey_api\verify-seam.ps1 -Before <改之前的備份> -After <改完的檔>
```

**exit 0 才算過。** 另外請學員秀 `git diff --stat`：`pages/survey/` 必須是 0 行變更。

如果他的後端契約逼得前端要改（例如 Q2 選了回 ISO 8601、或欄位改名），
**那不是扣分，是這一關最好的教材**：讓他親眼看到「後端一個決定，前端就得跟著動」，
再問他一句——**「如果前端已經上線給一千個人用了呢？」**
