# Step 1｜為什麼要有 harness？（後端版）

## harness 是什麼（三句話）

- harness 就是你交給 AI 的一套「規矩」：**專案規則**（CODE-RULES-api）＋**系統文件**（SRS／SDD）＋**標準範本 API**（薄 Controller → Service → EF Core 的既有寫法）。
- 沒有它，AI 每次都在「隨興發揮」：分層、驗證、狀態碼、例外處理全憑它當下高興，同一句需求今天做出來跟明天不一樣。
- 有了它，AI 產出從「路人硬湊、跑得起來但不敢上線」變成「像老手照團隊規矩寫、能直接進 code review 的後端」。

> 前端課你比的是「畫面像不像同一個團隊做的」；這堂課比的是「程式**敢不敢上線**」。
> 沒 harness 那版能新增裝備，但它同時開了 SQL Injection、吞掉例外、帳密寫死在原始碼——這才是後端最貴的坑。

---

## 這關 10 分鐘要看什麼

1. 打開 `demo/PROMPT.md` — 看清楚：兩版給 AI 的需求**同一句**，只差有沒有附上團隊規矩。
2. 打開 `COMPARE.html`（雙擊即可，免安裝、免連網）——左右並排兩份程式碼，**紅底＝違規、綠底＝合規**，每行都有白話註解，上方一張 12 項差異總表。深淺色都可讀，右上角可切換。
3. 對照 `demo/no-harness.cs`（沒 harness）與 `demo/with-harness.cs`（有 harness）原始檔，照下面的表逐項比。
4. 兩份都是「新增裝備」的 API，功能目標一樣——你要盯的是「差在哪、會出什麼事」。

## 對照表：差在哪，會出什麼事

| # | 觀察點 | 沒 harness | 有 harness | 白話講「會出什麼事」 |
|---|---|---|---|---|
| 1 | 分層架構 | 查詢／SQL／商業邏輯全塞 Controller | Controller 薄委派 → Service | 全攪一起的檔案沒人敢改，一動就連坐；分層後各司其職、好測好改 |
| 2 | 相依取得 | 方法內 `new` 連線、連線字串＋帳密硬編碼 | 建構式注入 DbContext／Mapper | 帳密寫死在原始碼＝上 git 就外洩；硬 new 也沒法在測試裡替換 |
| 3 | SQL 安全 | 字串拼接組 SQL | EF Core 查詢、參數化 | 拼字串＝SQL Injection 破口，保管人欄位打個 `';DROP` 就能砸你的資料表 |
| 4 | 請求驗證 | 散裝參數、零驗證 | DTO ＋ DataAnnotations | 空值、負數量、亂填 status 通通進資料庫，資料從第一天就是髒的 |
| 5 | 狀態碼 | 不管成敗一律回 200 | 201 建立／400 驗證／404 查無 | 前端無從判斷成功失敗，只能猜；監控也抓不到錯誤率 |
| 6 | 回應封裝 | 裸匿名物件，每支 API 各異 | 統一 `ModelResult` 封裝 | 每支 API 回傳長不一樣，前端要為每支寫一套解析，介接成本爆增 |
| 7 | 錯誤鍵命名 | 無錯誤鍵；欄位 PascalCase 混亂 | 框架回 400，錯誤鍵 camelCase | 前端拿不到「哪個欄位錯」，只能整包塞一個紅字，使用者不知道要改哪 |
| 8 | 例外處理 | blanket try/catch 吞例外，DB 斷線也回 200 | 只轉預期失敗，未預期上拋 500 | 吞掉例外＝故障被藏起來，資料沒存進去卻回你「成功」，最難查的 bug |
| 9 | 編碼產生 | 時間戳硬湊，不符規則、不保證唯一 | 交易內同前綴 MAX+1 ＋唯一索引 | 編碼撞號或格式亂掉，倉庫盤點對不上單，出貨拿錯裝備 |
| 10 | Location 標頭 | 無 | 201 + `CreatedAtAction` 帶 Location | 前端新增完不知道新資源在哪，只能再打一次查詢，多一趟往返 |
| 11 | 對外訊息 | 中英夾雜，還把 `ex.Message` 直接外露 | 全繁中、可安全外露 | 把例外原文丟給前端＝洩漏連線字串、資料表結構，等於送地圖給攻擊者 |
| 12 | 欄位命名一致性 | `Name`／`qty1`／`item_name`／`Qty` 各處不同 | 全對齊契約 camelCase | 命名各處不一，前後端對不上、欄位一改就整包錯位，維護惡夢 |

## 拿去現場實測：A/B 違規計分表

> **先誠實講清楚**：`demo/` 那兩份 `.cs` 是我們用 `demo/PROMPT.md` 裡**固定的兩版 prompt** 各跑一次、
> 挑出來當教材的**策展成品**，不是每次都會一模一樣重現的實驗。所以別把它們當「鐵證」——
> 要信，就**自己拿去現場實測一遍**。

做法很簡單：打開 `demo/PROMPT.md`，把**版本 A（沒 harness）**貼給你自己的 AI 跑一次、
把**版本 B（有 harness）**也貼給它跑一次，各自產出一份 `.cs`，然後照下表**逐項打違規分**
（每項：這一版有違規記 **1**、合規記 **0**），最後把兩版的違規分數加總來比。

| # | 可勾稽分項（每項 0＝合規／1＝違規） | 你的 A 版（沒 harness） | 你的 B 版（有 harness） |
|---|---|:---:|:---:|
| 1 | 商業邏輯／SQL 塞在 Controller，沒有分出 Service 層 |  |  |
| 2 | 方法內 `new` 連線，或連線字串／帳密硬編碼在程式裡 |  |  |
| 3 | 用字串拼接組 SQL（沒有參數化／沒走 ORM） |  |  |
| 4 | 沒有請求 DTO 或沒有欄位驗證（空值、負數量、亂填照收） |  |  |
| 5 | 不管成敗一律回 200（沒有 201／400／404） |  |  |
| 6 | 回應是裸物件／匿名物件，沒有統一封裝 |  |  |
| 7 | 驗證錯誤沒有 camelCase 欄位錯誤鍵（前端拿不到是哪欄錯） |  |  |
| 8 | blanket try/catch 把例外吞掉（DB 出錯也回「成功」） |  |  |
| 9 | 編碼用亂數／時間戳硬湊，不符「前綴-流水3碼」、不保證唯一 |  |  |
| 10 | 新增成功沒有回 Location 標頭 |  |  |
| 11 | 對外訊息中英夾雜，或把 `ex.Message`／例外原文外露 |  |  |
| 12 | 欄位命名各處不一致（PascalCase／snake_case／`qty1` 混用） |  |  |
| — | **違規分數合計（越低越好）** |  |  |

**怎麼判讀**：正常情況下 A 版違規分數會明顯高於 B 版。**比的是「違規數的落差」**，
不是要求你重現我們這兩份的逐字內容。若你的 A 版剛好也守了幾條，那也很好——代表你的 AI 底子不錯，
但只要需求換難一點、規則換多一點，沒 harness 的那版就會開始崩（尤其例外處理與 SQL 安全這種「跑得起來但會出事」的坑），這正是 harness 要解決的事。

## 一句話結論

**harness 不是限制 AI，是讓 AI 像你團隊的資深工程師。**
