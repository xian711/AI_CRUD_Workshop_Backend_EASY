# Step 1｜為什麼要有 harness？（後端版）

## harness 是什麼（三句話）

- harness 就是你交給 AI 的一套「規矩」：**專案規則**（CODE-RULES-api）＋**系統文件**（SRS／SDD）＋**標準範本 API**（薄 Controller → Service → EF Core 的既有寫法）。
- **它不是用來讓 AI 寫得比較好看**——現在的模型不給規矩也寫得出漂亮、能跑、分層正確的 API。
- 它是用來決定「**這些決定誰做**」：回應長什麼樣、編碼怎麼產、欄位叫什麼、訊息用哪國語言。沒 harness，這些全是 AI 當下自己發明的，跟你們團隊無關。

> 生活比喻：請一個很厲害的木工來做櫃子。不給圖，他做得又快又漂亮——但抽屜高度、把手樣式、木料顏色全是他自己決定的，跟你家其他櫃子搭不起來。
> **harness 就是那張圖。** 它不是在管他手藝好不好，是在管「尺寸照誰的」。

## 這關 10 分鐘要看什麼

1. 打開 `demo/PROMPT.md` — 看清楚：兩版給 AI 的需求**同一句**，只差有沒有附上團隊規矩。
2. 打開 `COMPARE.html`（雙擊即可，免安裝、免連網）——左右並排兩份程式碼，每行都有白話註解，上方一張 3 項差異總表。深淺色都可讀，右上角可切換。
   **注意左邊那版也有綠底**——那是它自己就做對的地方，我們誠實標出來。
3. 對照 `demo/no-harness.cs`（沒 harness）與 `demo/with-harness.cs`（有 harness）原始檔。
4. 兩份都是「新增裝備」的 API，功能目標一樣——你要盯的是「**每個決定是誰做的**」。

## 對照表：三項差異

> 這三項是 **2026-08-19 拿現在的模型實跑版本 A 之後重寫的**，不是沿用舊結論。舊版有 12 項，其中 8 項現在的模型自己就做對了。

| # | 觀察點 | 沒 harness | 有 harness | 白話講「會出什麼事」 |
|---|---|---|---|---|
| 1 | **回應格式從哪來** | 自己發明一個 `EquipmentResponse` record | 統一 `ModelResult<T>`（`success`／`message`／`data`） | 每支 API 回傳長不一樣，前端要為每支寫一套解析，介接成本爆增 |
| 2 | **業務規則與對外訊息從哪來** | id 用 `Guid`、**完全沒有 code 這個概念**、驗證訊息是英文、錯誤鍵預設 PascalCase、欄位自己取名（`Quantity`／`Specification`） | 照契約：`E-###`、code 為「前綴-流水3碼」交易內取號、繁中訊息、camelCase 錯誤鍵、13 欄逐字對齊前端 | 編碼規則、欄位名、訊息語言都對不上前端與既有系統，等於做了一支沒人能接的 API |
| 3 | **多出來的東西** | **兩版都會自己多做**——實跑時它多加了一個沒人要的 `GetById` 端點、Swagger、兩個時間欄和一個索引 | 一樣擋不住 | **harness 管「怎麼寫」，不管「做多少」**。範圍要靠 step3 的 SCOPE 六題管，不是靠 harness 擋 |

**第三列是誠實揭露。** 它承認 harness 的邊界，也把「範圍怎麼管」的球接給 step3。

### 它自己就做對了什麼（也要講）

實跑版本 A 時，這幾件事**它完全沒被教就做對了**——所以不要拿這幾項來說服人：

- 分層：Controller 薄委派 → Service → DbContext
- 相依注入：建構式注入，連線字串走設定檔，**沒有把帳密寫死在程式裡**
- 資料存取：EF Core 參數化，**沒有字串拼接 SQL**
- 請求驗證：自己寫了 DTO ＋ DataAnnotations
- 狀態碼：201 ＋ `CreatedAtAction` 帶 Location、400 由框架回
- 例外處理：用 `AddExceptionHandler` ＋ ProblemDetails，**沒有 blanket try/catch**

## 拿去現場實測：A/B 決定來源計分表

> **先誠實講清楚**：`demo/` 那兩份 `.cs` 是我們用 `demo/PROMPT.md` 裡**固定的兩版 prompt** 各跑一次的產出，
> 不是每次都會一模一樣重現的實驗。所以別把它們當「鐵證」——要信，就**自己拿去現場實測一遍**。

做法：打開 `demo/PROMPT.md`，把**版本 A（沒 harness）**貼給你自己的 AI 跑一次、
把**版本 B（有 harness）**也跑一次，然後照下表逐項打分（**1 ＝ AI 自己決定的、0 ＝ 照你們規矩的**）。

|---|---|:---:|:---:|
| 1 | 回應形狀（有沒有統一封裝、封裝長什麼樣） |  |  |

| 4 | 請求／回應的欄位名稱（跟前端契約對不對得上） |  |  |
| 5 | 驗證錯誤訊息的語言 |  |  |
| 6 | 驗證錯誤鍵的大小寫慣例 |  |  |
| 7 | 路由字串 |  |  |
| — | **「AI 自己決定」的項數合計（越低越好）** |  |  |
| ＋ | **它多做了幾個沒人要求的端點／欄位／套件？**（兩版都要數） |  |  |

**怎麼判讀**：A 版的「自己決定」項數會明顯高於 B 版；但**最後那一列兩版通常差不多**——
這正是重點：harness 收斂「怎麼寫」，收斂不了「做多少」。

## 一句話結論

**harness 不是讓 AI 寫得更好，是讓 AI 的決定變成你們團隊的決定。**
