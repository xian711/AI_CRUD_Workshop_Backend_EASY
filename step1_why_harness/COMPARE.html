為什麼要 harness？同一句「幫我寫一個新增裝備的 API」，有沒有給團隊規矩，AI 產出天差地遠

左邊是沒有 harness、AI 憑一句話自由發揮的產出；右邊是附上團隊規矩後的產出。 兩份都是「新增裝備」API，功能目標一樣——差的不是「有沒有做出來」，是「能不能安全上線、像不像同一個資深後端寫的」。 紅底是違規、綠底是合規，滑到程式碼看每一行的白話註解。

#觀察點沒 harness有 harness對應規矩
1分層架構全塞 Controller，查詢／SQL／商業邏輯攪一起Controller 薄委派 → Service 處理分層
2相依取得方法內 new 連線、連線字串＋帳密硬編碼建構式注入 DbContext / Mapper分層
3SQL 安全字串拼接組 SQL，SQL Injection 破口EF Core 查詢，參數化、無拼接資料存取
4請求驗證散裝參數、零驗證，空值負數亂填照收DTO ＋ DataAnnotations 宣告式驗證DTO
5狀態碼不管成敗一律回 200201 建立 / 400 驗證 / 404 查無契約
6回應封裝裸匿名物件，每支 API 格式各異統一 ModelResult 封裝契約
7錯誤鍵命名無錯誤鍵；欄位 PascalCase 混亂框架回 400，錯誤鍵 camelCaseDTO
8例外處理blanket try/catch 吞例外，DB 斷線也回 200只轉預期失敗，未預期上拋 500例外
9編碼產生時間戳硬湊，不符規則、不保證唯一交易內同前綴 MAX+1 ＋唯一索引編碼
10Location 標頭無；前端拿不到新資源位置201 + CreatedAtAction 帶 Location契約
11對外訊息中英夾雜，還把 ex.Message 直接外露全繁中、可安全外露，不夾例外細節例外
12欄位命名一致性Name／qty1／item_name／Qty 各處不同全對齊契約 camelCase 欄位契約
