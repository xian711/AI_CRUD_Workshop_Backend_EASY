為什麼要 harness？同一句「幫我寫一個新增裝備的 API」，有沒有給團隊規矩，AI 的決定從哪裡來

左邊是沒有 harness、AI 憑一句話自由發揮的產出；右邊是附上團隊規矩後的產出。 先講清楚：左邊那版寫得很好。分層、注入、EF Core 參數化、DTO 驗證、201＋Location，它自己全都做對了—— 這就是為什麼綠底在左邊也會出現。真正的差別不是「品質好不好」，是每一個決定是誰做的： 回應長什麼樣、編碼怎麼產、欄位叫什麼、訊息用哪國語言——沒 harness 的那版全部自己發明，跟你們團隊無關。 滑到程式碼看每一行的白話註解。

三項差異（2026-08-19 用現在的模型實跑後重寫）

#觀察點沒 harness有 harness對應規矩
1回應格式從哪來自己發明一個 EquipmentResponse record，每支 API 各長各的統一 ModelResult<T>（success/message/data）契約
2業務規則與對外訊息從哪來id 用 Guid、完全沒有 code 這個概念、驗證訊息是英文、錯誤鍵預設 PascalCase、欄位自己取名（Quantity／Specification）照契約：E-###、code 為「前綴-流水3碼」交易內取號、繁中訊息、camelCase 錯誤鍵、13 欄逐字對齊前端契約編碼
3多出來的東西兩版都會自己多做。實跑時它多加了一個沒人要的 GetById 端點、Swagger、CreatedAt／UpdatedAt 兩欄和一個索引。harness 管「怎麼寫」，不管「做多少」——範圍要靠 step3 的 SCOPE 六題管。誠實揭露
為什麼從 12 項收成 3 項？舊版比的是「分層有沒有亂、有沒有拼 SQL、帳密有沒有硬編碼、例外有沒有吞掉」共 12 項。 2026-08-19 拿現在的模型實跑版本 A，其中 8 項它自己就做對了——那是舊模型才會犯的錯。 留著只會讓學員覺得這個對照不公平，harness 的說服力反而被削弱。 對照基準會過期，每換一代模型就要實跑一次重寫。
