請求的一生（先建立整體感）

動手前先記住這條動線。這堂課做的每一件事，都是在這條線上補齊某一段：

瀏覽器（前端頁面） │ useFetch('/api/equipment/items') ▼ Nuxt devProxy（前端轉呼叫，避開跨網域） │ HTTP GET/POST/PUT/DELETE ▼ Controller（薄委派，只做「呼叫 Service → 對映狀態碼」） │ ▼ Service（商業邏輯全在這：產 id、算 code 編碼、查無回失敗） │ ▼ EF Core（把物件翻成 SQL，參數化、防注入） │ ▼ PostgreSQL（資料表 equipment_item，真正落地的地方） │ 一筆一筆存著，F5 不會消失 ▼ 原路回來 → JSON → 前端畫面

前端課只做到「瀏覽器」那一格（資料在記憶體）；這堂課把 devProxy → Controller → Service → EF → PostgreSQL 這一整段接起來。資料在 PostgreSQL 裡查得到，才叫真的持久化。

為什麼要有 harness？（後端版）

10 分
🎯這一步要做到
  1. 用「同一句後端需求、只差有沒有附規矩」的兩個產出，看出差別在哪一層。
  2. 知道 harness 真正在管什麼：不是「AI 寫得好不好」，是「這些決定誰做」。
  3. 知道 harness 的邊界：它管「怎麼寫」，管不了「做多少」。
👣跟著做

harness 就是你交給 AI 的一套「規矩」：專案規則（CODE-RULES-api）＋系統文件（SRS／SDD）＋標準範本 API（薄 Controller → Service → EF Core 的既有寫法）。

先破除一個誤會：現在的模型不給規矩也寫得出漂亮的 API。2026-08-19 實跑沒 harness 那版，它自己就做出分層、建構式注入、EF Core 參數化、DTO 驗證、201＋Location、全域例外處理——一項都不用教。所以 harness 要解決的不是「寫得爛」。

它解決的是：回應包成什麼形狀、id 長什麼樣、有沒有「品項編碼」這個概念、欄位叫 Quantity 還是 qty、錯誤訊息用中文還是英文——沒 harness，這些全是 AI 當下自己發明的，跟你們團隊、跟前端已經做好的頁面完全對不上。

生活比喻：請一個很厲害的木工做櫃子。不給圖，他做得又快又漂亮，但抽屜高度、把手樣式、木料顏色全是他自己決定的，跟你家其他櫃子搭不起來。harness 就是那張圖——不是在管他手藝，是在管「尺寸照誰的」。

  1. 打開 step1_why_harness/demo/PROMPT.md——確認兩版給 AI 的需求是同一句，只差有沒有附規矩。
  2. 雙擊 step1_why_harness/COMPARE.html（免安裝、免連網）：左右並排兩份程式碼，每行有白話註解，上方一張 3 項差異總表。注意左邊那版也有綠底——那是它自己就做對的地方，我們誠實標出來。
  3. 對照 demo/no-harness.cs 與 demo/with-harness.cs，照 3 項總表逐項比。
👀你應該看到

兩份都是「新增裝備」的 API，功能一樣、品質也都不差。差的是每一個決定是誰做的：

#觀察點沒 harness有 harness會出什麼事
1回應格式從哪來自己發明一個 EquipmentResponse record統一 ModelResult<T>每支 API 回傳長不一樣，前端要為每支寫一套解析
2業務規則與對外訊息從哪來id 用 Guid、完全沒有 code 這個概念、訊息是英文、錯誤鍵 PascalCase、欄位自己取名照契約：E-###、code「前綴-流水3碼」交易內取號、繁中訊息、camelCase 錯誤鍵、13 欄對齊前端編碼、欄位名、訊息語言全對不上前端，做出一支沒人能接的 API
3多出來的東西兩版都會自己多做——實跑時它多加了一個沒人要的 GetById 端點、Swagger、兩個時間欄和一個索引harness 管「怎麼寫」，不管「做多少」；範圍要靠 step3 的 SCOPE 六題管

它自己就做對了什麼（也要講）：分層、建構式注入（帳密沒寫死）、EF Core 參數化（沒拼 SQL）、DTO ＋ DataAnnotations 驗證、201＋Location、全域例外處理（沒有 blanket try/catch）。不要拿這幾項來說服人——學員一看就知道不公平。

⚠️常見坑
  • 別把 demo 那兩份 .cs 當「鐵證」——它們是用固定 prompt 各跑一次的產出，不是每次一字不差重現。要信，就自己拿 demo/PROMPT.md 的兩版 prompt 各跑一次、照「A/B 決定來源計分表」逐項打分。
  • 這個對照的基準會過期。舊版有 12 項對照，2026-08-19 實跑後發現其中 8 項（分層、SQL 安全、帳密硬編碼、例外吞掉…）現在的模型自己就做對了，已刪除。每換一代模型都要重跑一次、重寫這張表，並把結果記進 step1_why_harness/README.md 的實測紀錄表。
  • 比的是「AI 自己決定了幾項」的落差，不是逐字內容。
💡為什麼
harness 不是讓 AI 寫得更好，是讓 AI 的決定變成你們團隊的決定。 沒 harness 那版做得又快又整齊，但它發明的回應形狀、id 格式、欄位名稱、訊息語言，跟你們前端已經做好的頁面完全對不上——接不起來的好程式，等於白做。同一句需求，差的不是 AI 智商，是規格從誰那裡來。

40 分

① 讀 PRD（3.1）

打開 step3_new_module/PRD-中心裝備物資-後端.md。這份 PRD 從前端課的成品逆向整理而來——記的是「現況契約」，連缺口都照實記。核心觀念：前端的型別欄位叫什麼、哪些必填，後端就照著做；欄位名一個都不能改，改了前端就接不上。 契約是 13 欄（必填 6：categoryKey、name、qty、unit、spec1、status；選填 5；系統產生 2：id、code），回應另加 updatedAt、一律 camelCase。標「待釐清」的地方＝待你決策。

你：貼【起手 prompt】 ▼ AI：依序讀 CLAUDE.md → AGENTS.md → 其餘 harness 規則 → PRD ▼ AI：先不寫程式，改用「選擇題」問你範圍（5-7 題，每題附建議＋理由） ▼ 你：一題一題拍板（可採納建議，但先想清楚為什麼） ▼ AI：輸出 SRS-delta／SDD-delta（寫進 docs/）＋任務清單（T1、T2…），停下等你確認 ▼ 你：說「開工」 ▼ AI：依範本分層逐任務開發（Entity → migration → DTO → Mapper → Service → Controller → seed → 測試），每完成一個回報一行

③ 一題一題拍板（SCOPE 六題）

AI 會用選擇題把 PRD 第 5 節的岔路攤開來問你。這六題是這堂課的核心決策，每題都是在「完整需求」和「兩小時課堂」之間做取捨——做取捨的人是你：

#AI 會問（大意）
Q1code（如 IT-LAP-001）誰產生、怎麼保證同前綴流水號不撞？
Q2id（如 E-001）怎麼產？種子的顯式 id 與新增的自動 id 怎麼銜接？
Q3分類／項目字典要不要建資料表，還是當程式常數？
Q4刪除是硬刪還是軟刪？

前端課的課後驗收題是做一份課程回饋問卷。學員做出來了，但資料存在瀏覽器 localStorage，換一台電腦就看不到。程式裡留了一行：

// TODO: DEV 串接 POST /api/survey

這一關就是把那一行變成真的。完整說明在 step6_survey_api/README.md，起手 prompt 在 step6_survey_api/PROMPTS.md。

step3 裝備物資step6 問卷 API
需求從哪來課程準備好的後端 PRD前端課的 PRD，沒有為後端改寫過一個字
端點名稱誰定課程訂好的凍結——前端那行 TODO 怎麼寫就怎麼做
驗收幾路三路（Swagger／test／psql）四路，多一路「接縫驗證」
👀怎麼證明「呼叫端一行不用改」

這句話不是口號，它有可機器判定的定義：對外匯出的東西一個字都沒變。跑這支腳本，它會比對接縫 before／after 兩版的四樣東西——匯出的名字、契約欄位、composable 回傳的 key、每個 function 的簽章：

powershell -ExecutionPolicy Bypass -File .\step6_survey_api\verify-seam.ps1

四樣完全相同才 exit 0。有你自己前端專案的話，跑完再看 git diff --stat——pages/survey/ 必須是 0 行變更。

⚠️常見坑
  • 不要另外寫一份後端 PRD。真實工作拿到的需求就是別人寫的，不會為你重寫。你的工作是把它翻譯成後端契約，模糊處用選擇題問人。
  • 不要改端點名稱。AI 很愛把 /api/survey 改成 /api/survey/responses。契約以已經存在的那一端為準，不是以「哪個比較漂亮」為準。
  • SCOPE 六題先自己答完再看答案。答案在 instructor/，直接抄等於跳過這一關最重要的練習。
💡為什麼
「留接縫」不是寫一行 TODO 註解就算數。真正的接縫是「把會變的東西關進一個檔案裡，讓外面的人看不到它變過」。前端課把 localStorage 的細節全關在 useSurveyResponses.ts 裡，只對外露出三個名字——所以今天換成打 API，外面完全無感。

生活比喻：家裡的插座。你換冷氣、換冰箱、換烤箱，插頭形狀都一樣，牆壁一次都沒敲過。插座規格就是接縫；定好接縫，兩邊才能各自換。
