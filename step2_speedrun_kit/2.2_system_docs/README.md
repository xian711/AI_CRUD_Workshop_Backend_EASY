## 第 11 章挑六個決策講白話

第 11 章共 14 條（D1–D14b）。課堂先懂這六個，就抓到範本的骨幹：

| ID | 決策 | 白話 |
|----|------|------|
| **D1** | JSON 契約 camelCase（DB 仍 snake_case） | 前端型別就是 camelCase，契約跟著它走，前端接 API 免逐欄改名；DB 底層照原單位範本慣例用 snake_case，中間自動轉換 |
| **D4** | 回應統一 `ModelResult<T>` 封裝 | 成功失敗都包一層 `{success,message,data}`，前端與監控靠它判斷可用性；代價是前端多一層 `.data` unwrap |
| **D5** | DELETE 成功回 204 無封裝 | 刪掉了沒東西好回，依 HTTP 語意回 204 空主體——這是全案唯一不套 ModelResult 的地方 |
| **D6** | id 用 SQL SEQUENCE 產生 | 交給資料庫發號碼，交易安全、不會兩個請求搶到同一個 id；比前端「找目前最大號+1」穩 |
| **D9** | PUT 不做 upsert（不存在回 404） | 更新一個不存在的 id 就回 404，不會偷偷幫你新增一筆——對齊前端「找不到就報錯」的語意 |
| **D11** | Service 不做 blanket try/catch | 只有「查無資料」這種預期失敗才回 404；DB 斷線這種意外**不攔**、直接上拋回 500。全包 try/catch 會把「伺服器掛了」誤報成「找不到資料」 |

> 想更完整：D2（用 PostgreSQL）、D7（DateOnly 避時區陷阱）、D10（positionTitle 不落 DB）、D12（updatedAt 定位）、D14b（bloodType 選填＝跨課相容）也值得一看，同在 §11 表格。

## 建議讀法

- 第一次：只讀上面「五個地方」的表格與本頁白話，夠你理解範本。
- 要動手改契約／綱要／驗證時：再翻對應章節的完整內容。
- 想知道「這條需求從哪來」：查 SRS 的 FR-B / BR-B / NFR-B 編號（設計文件各處會回引這些編號）。
