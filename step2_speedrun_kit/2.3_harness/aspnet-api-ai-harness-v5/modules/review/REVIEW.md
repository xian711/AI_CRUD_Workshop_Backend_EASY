# REVIEW 模組（審查閘門）

## 目的

在 BUILD 之後、交付之前，用結構化審查取代人工逐項檢查。工程師只看審查報告與 ❌ 項，不必逐檔逐欄位確認。

## 審寫分離

- 審查與產碼**不得在同一對話**。開新對話執行 `/review-loop`。
- 審查者只指出問題：不改程式碼、不重新設計、不裁決規格疑義。
- 業務疑義標 `[SA 確認]` 升級處理；已確認的技術決策不翻案。
- 最終判斷與採用權在工程師；AI 審查是過濾器，不是問責主體。

## 三層審查

1. **SPEC 一致性**（需要 SPEC）：FR 欄位完整、狀態名稱與 SPEC 一致、BR 正確實作（必填、狀態轉換、計算邏輯）、角色權限隔離、資料範圍正確（不跨層外洩）、程式生成的 OpenAPI 與 SPEC 契約一致。
2. **通用系統規範**（不需 SPEC，依業界慣例即可判斷）：見 `review-checklist.md`；命名與資料表對照 `harness/CODE-RULES-api.md` / `CODE-RULES-ui.md`（只讀 diff 涉及的那份）。
3. **流程合理性**：條件顯示順序（先選父層才選子層）、未儲存離開的 dirty check、不可逆操作警告、時間與金額格式統一。
4. **文件同步**（段落收尾後的 review）：SPEC 狀態與程式一致、UML 圖未過時（過時的圖比沒圖更糟）。

## 雙向偵測

**設計遺漏（DG）**——找缺的：

- DG-01 外部依賴失敗的 fallback（DB / SMTP / 第三方 API）
- DG-02 錯誤復原路徑與 Transaction rollback 後的狀態
- DG-03 邊界條件：空輸入、重複執行、超大資料量
- DG-04 NFR 是否有對應設計（不能只寫在需求裡）
- DG-05 設定缺失 / 初始化失敗的行為
- DG-06 通知 / 回呼的送達確認與補送

**過度設計（OE）**——找多的：

- OE-01 複雜度與需求不匹配
- OE-02 不必要的中介服務（MQ / Cache）
- OE-03 不必要的維運設施（Dashboard / 分散式追蹤）
- OE-04 無對應需求的預防性彈性（抽象層 / Plugin / Factory / Strategy）
- OE-05 為抽象而抽象的過深分層

過度設計與設計遺漏**同等重要**：不只找缺漏，也找冗餘。

## 嚴重度

| 等級 | 意義 | 處置 |
|---|---|---|
| ❌ Critical | 違反 SPEC、違反鐵律、安全問題 | 阻擋完工，寫入 `harness/LOOP.md` 待辦 |
| ⚠️ Warning | 可疑偏離、慣例不一致 | 建議修正 |
| 💡 Suggestion | 改善建議 | 選擇性採納 |

不確定時往低降級（❌→⚠️→💡），避免誤報。

## 報告原則

- **有憑據**：每項引用 SPEC 編號或 `file:line`。
- **可行動**：每個 ❌ / ⚠️ 附具體建議方向；禁止「建議再檢視」這類空話。
- **比例原則**：報告尾列出「已確認、不在審查範圍的技術決策」，避免反覆翻案。
- **覆蓋矩陣**：列出每條 FR 的實作與測試對應狀態，並標出無任何需求對應的「孤立設計」。
- ❌ 項修正後重審，通過才進 DONE。
