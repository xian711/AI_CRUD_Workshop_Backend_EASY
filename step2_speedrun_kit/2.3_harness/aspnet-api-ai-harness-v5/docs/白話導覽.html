這套 Harness 每個檔案為什麼存在——白話、有圖、有例子

不是 AI 變聰明，而是 Harness 讓 AI 被正確約束
解什麼問題20 行程式碼開發旅程資料夾地圖逐項說明常見疑問上路三步

一、Harness 到底在解什麼問題

你跟 AI 說「幫我做一個裝置查詢 API」。十分鐘後它交出來：多了一個你沒要求的匯出 CSV、清單回傳的是寫死的假資料（看起來能動，其實根本沒接資料庫）、還順手把你別的檔案「優化」了一輪。你花在收拾的時間，比自己寫還久。

這不是 AI 不聰明，是它有四個天生的毛病。Harness 的每個機制都對著其中一個：

AI 的毛病具體長相Harness 的解法
愛發揮沒人要求的功能順手加、規格沒寫的自己腦補SDD first：先有規格再有程式，範圍外預設移除（SPEC.md＋鐵律 1）
裝完成沒做完的功能回假資料、效能數字用猜的誠實原則：未實作回 501、mock 必標示、數字標 [待實機]（鐵律 2）
會漂移對話聊久了，前面立的規矩慢慢忘光規則常駐（CLAUDE.md）＋開場自動重灌（SessionStart hook）
重複踩坑上週踩過的坑，這週換個對話又踩一次錯誤防範庫（LESSONS.md）＋事件表強制回填

二、用 20 行程式碼看差別

同一句需求：「幫我做一個裝置查詢 API」。同一個 AI 模型，差別只在有沒有 harness。

❌ 沒有 harness——AI 交出這個
[HttpGet("GetAllDevice_List")]   ← ② 命名自創一格
public IActionResult GetAllDeviceList()
{
    return Ok(new[] {            ← ③ 寫死的假資料
      new { id=1, name="裝置A", status="OK" },
      new { id=2, name="裝置B", status="OK" }
    });
}

[HttpDelete("DeleteDevice")]     ← ① 沒人要求的刪除
public IActionResult DeleteDevice(int id)
{
    _db.Devices.Remove(
      _db.Devices.Find(id));     ← ④ 商業規則用猜的
    _db.SaveChanges();
    return Ok("刪除成功");
}
✅ 有 harness——同一句需求
/// <summary>查詢裝置清單（FR-01）</summary>
[HttpGet]                        ← 命名照 CODE-RULES
public async Task<IActionResult> GetListAsync(
    [FromQuery] DeviceQueryDto query)
{
    var result = await
      _deviceService.GetListAsync(query);
                                 ← 分層：邏輯在 Service
    return result.Success
      ? Ok(result)
      : BadRequest(result);      ← 統一 envelope
}

// SPEC 沒有刪除需求 → 不寫（鐵律 1）。
// 之後要加，AI 會先用選擇題問你 BR：
//   誰能刪？軟刪還硬刪？

左邊四個記號就是第一節的四大毛病現形。最危險的是 ③——看起來能動，所以沒人發現它是假的，直到上線那天。

差異沒 harness有 harness靠哪個機制
範圍順手加了沒人要的刪除規格沒寫的不做鐵律 1 SDD first＋SPEC 編號
誠實假資料回 200 冒充完成真的接 Service；沒定案的回 501鐵律 2 誠實原則
慣例命名、分層自由發揮跟公司既有專案長一樣CODE-RULES-api.md
決策商業規則自己猜用選擇題問人再動手鐵律 5 越權標記＋鐵律 6 互動決策
可追溯程式對應哪個需求？沒人知道標 FR-01，review 逐條對帳SPEC 編號＋覆蓋矩陣

三、一次開發會經過什麼

你提出需求
→
CLAUDE.md 路由判斷走哪條 loop
→
/api-loop 或 /crud-loop讀 SPEC 與 TASKS
→
產出一項任務＋立刻驗證
失敗最多修 2 輪，過了才勾
→
/milestone-loop文件同步＋重構掃描
→
/review-loop開新對話審查
有 ❌ 退回修
→
候選完工由人最終核可

記住三個節奏：

  1. 平常：一個 loop 做一項任務，做完馬上驗，驗過才算數。
  2. 段落收尾：/milestone-loop 讓文件跟上程式，順手掃冗餘。收尾後下一段落建議開新對話——context 歸零省 token、規則不衰減，狀態由 LOOP.md 接手。
  3. 完工前：開新對話跑 /review-loop，全綠才能說「候選完工」——最後拍板的永遠是人。

四、資料夾地圖

五、逐項說明（是什麼／為什麼／舉例）

根目錄三份

CLAUDE.md——路由器

是什麼AI 每次開對話自動讀的檔，只有 20 幾行：鐵律濃縮＋「你要做什麼 → 用哪個指令」對照表。
為什麼這個檔每次對話都付 token。細節放在用到才載入的 command 裡，常駐的只留路標——總機不用會修機器，只要知道轉給誰。
舉例你說「幫我加個查詢畫面」→ AI 從路由表看到「後端＋畫面 → /crud-loop」→ 走對流程，而不是憑感覺直接改檔案。

HARNESS.md——規則總部

是什麼六條鐵律、三種 Mode、驗證分級、模型分級、完工三關的唯一原始出處。
為什麼規則散在十個檔案，AI 每次讀到的版本可能不一致；集中一處，其他檔案只引用。
舉例鐵律 2 誠實原則——做不完的端點必須回 501，不准回寫死的假資料。假的 200 比沒做更危險：demo 那天才發現全是假資料就來不及了。

USER-GUIDE.md——使用手冊

是什麼5 分鐘上手＋每個檔案的一行式速查表。
為什麼新人第一份要讀的檔。本導覽講「為什麼」，它講「怎麼用」，互補。

.claude/——給 Claude Code 的自動化

五個指令（commands/）

指令一句話防的坑
/api-loop做一個後端 API 的固定流程每次 prompt 品質不一——一句指令觸發同樣的完整流程
/crud-loopAPI＋畫面一起做畫面返工最貴——先審 UI Spec 再產碼；新建超過 3 個元件先用選擇題問你
/ui-loop只做畫面雛形（無後端）雛形不需要 API 產物；美感 AI 不可靠，一律標「待人工目視」
/milestone-loop段落收尾：文件同步＋重構掃描＋清冗餘註解程式迭代文件必掉隊；「過時的圖比沒圖更糟」
/review-loop完工審查（必須開新對話）自己審自己一定放水——見下方常見疑問 Q1
舉例/api-loop 的驗證回圈：AI 寫完 API 不是說「完成了」就結束——要實際啟動服務、用 curl.exe 打真的請求、貼真實回應給你看。跑不起來就老實標 blocker，不准捏造輸出。

兩個技能（skills/）

是什麼aspnet-api-crud-sdd-loop（忘記打指令時 AI 仍會自動照流程走）、gis-frontend（地圖開發的專屬規則與坑）。
為什麼技能平常只佔一行描述的 token，講到相關話題才整份載入——專業領域規則「零常駐成本」。
舉例你直接說「幫我做個設備管理功能」沒打指令——skill 接住，自動照流程走，不讓 AI 自由發揮。

開場 hook（hooks/session-start.sh＋settings.json）

是什麼每次開新對話、或長對話被壓縮後，自動把鐵律／路由／完工三關的摘要重新塞進對話開頭。
為什麼對話越長，AI 對開頭規則的記憶越糊——像傳話遊戲傳到第 50 句。規則衰減靠 AI 自己記是記不住的，hook 是機器保證的重灌。
舉例長對話尾聲你說「順手加個欄位」。沒 hook：AI 早忘了路由表，直接動手。有 hook：規則剛被重灌，照樣走 /crud-loop。
要知道的一件事：第一次在這個資料夾啟動 Claude Code 會跳「是否信任此 hook」——按同意就好，之後不再問。

harness/——每次任務的工作檔

SPEC.md——規格（一切的源頭）

是什麼本次任務的規格範本：功能需求（FR）、商業規則（BR）、測試案例（TC）都有編號；API contract、Mermaid 圖、完工標準。
為什麼有編號才能對帳。審查時產「覆蓋矩陣」——每條 FR 有沒有對應程式和測試一眼看出；反過來也抓得出「沒有任何需求對應的程式」（AI 又發揮了）。
舉例FR-03：Given 未登入，When 呼叫查詢 API，Then 回 401。程式和測試都標 // FR-03，review 時矩陣上這格就是綠的。

TASKS.md——任務清單（WBS）

是什麼規格定案後 AI 展開的 checkbox 清單，每條標對應 FR 和驗證方式。
為什麼「做完了沒」不能靠印象。- [ ] 機器可掃；驗證通過才准勾，勾了就是有證據的。
舉例- [ ] T7 curl smoke（FR-01～03）｜驗證: L2——沒勾之前誰都不能說做完了。決定不做的要經你用選擇題核可、標 [-]，不准默默消失。

LOOP.md——目前狀態

是什麼現在進行到哪、這輪的待辦和決策。只記待辦，不記已完成。也是新對話續作的接手點。
為什麼記已完成會吃掉對話額度，還誘導 AI 自我感覺良好。進度看 TASKS、證據看 git、這裡只放還沒解決的事。
舉例昨天做到一半今天開新對話，說「繼續上次的進度」——AI 照路由表「接續上次進度」先讀本檔的 Next 欄，直接延續，不重新規劃、不從頭再問一遍需求。

LESSONS.md——踩坑紀錄

是什麼踩過的坑，固定格式「問題 → 原因 → 防範」，一行一坑；每個 loop 開工前 AI 先掃一遍。
為什麼AI 沒有跨對話記憶，同一個坑會無限重踩。回填不靠自覺，靠事件表 E1–E5 逐項對照（fix 修兩輪、review ❌、被人指正、驗證曾失敗、你否決過它的建議）——像餐廳關店檢查表，逐項勾而不是憑感覺。
舉例真實條目 LS-07：「PowerShell 打 curl 參數全錯 → curl 是別名 → 防範：一律明寫 curl.exe」。記下來之後這個坑再沒踩過。

CODE-RULES-api.md／CODE-RULES-ui.md——程式規範（按面向拆兩份）

是什麼後端（分層、命名、資料表、migration）和前端（框架慣例、API 封裝）細則各一份。技術棧綁定全集中在這裡——核心規則不綁棧，換技術棧只換這兩份＋templates。
為什麼純後端工作不必載前端規則，省 token；也防 AI 把前端慣例套到後端。
舉例AI 預設用它習慣的通用風格。有了這份，它寫的 Controller 分層、表命名（work_order_m 小蛇形）、審計欄位跟公司既有專案長一樣——review 的人不用重新適應。

modules/——需要才載入的細節

crud-ui/ 三件（UI 慣例、Design Token 規則、Design System 摘要）

是什麼表單互動慣例（必填加 *、危險操作二次確認…）、樣式 token 檢查規則、公司設計系統的摘要版。
為什麼完整設計文件太大，每次貼會爆 token；摘要一次寫好重複用。token 規則做成「可執行的檢查」——檢查 → 修正 → 複驗，閉環。
舉例AI 想寫 color: #FF0000 → token 檢查攔下 → 改成 var(--color-danger)。將來換主色改一個變數全站生效。

review/ 兩件（審查規則＋通用檢查清單）

是什麼審查的完整規則（三維度、嚴重度分級、申辯通道）＋不需要規格也能審的通用清單。
為什麼AI 不只會漏做（缺 fallback、缺邊界），也會多做（沒人要的抽象層、用不到的 Cache）。雙向偵測同時抓兩頭。
舉例申辯通道：Reviewer 標 ❌「刪除沒做軟刪除」，但規格明寫硬刪除——Coder 可拿規格條文要求重審那一條（限一次），不用去「修一個本來就沒錯的東西」。

verify/——驗證分級

是什麼L0（build）→ L1（測試）→ L2（curl 實打）→ L3（瀏覽器 E2E），永遠先跑便宜的。
為什麼各級成本差十倍以上。build 都不過就去測 E2E 是燒錢燒時間；L0 不過就不跑 L1，L3 預設跳過。
舉例E2E 裡外部付費 API 一律 mock——曾有測試直接打真的 AI API 把額度燒掉（LESSONS 記過這條）。

templates/、examples/、prompts/、scripts/、docs/

templates.http 測試檔、TDD 案例、mock 資料、Mermaid 圖骨架、接手舊系統盤點清單……AI 照範本填，不自由發揮——產出格式統一，review 的人每次看到的長相都一樣。
examples兩個填好的完整範例（派工單 API、設備 CRUD）。不會填 SPEC？抄這個，比讀十頁說明快。
prompts沒有 Claude Code 的環境（其他 AI 工具）用的濃縮 prompt，把 loop 精華壓成可貼上的幾段話。
scripts跑測試的統一入口（run-tests.ps1／.sh）——L1 驗證只有一個門。
docs簡報、網頁版手冊、三堂課流程、導入 FAQ、規則演進紀錄（每條規則當初踩了什麼坑才立的）。開發時用不到，備課和導入時用。

六、三個最常被問的「為什麼」

Q1：為什麼審查一定要開新對話？

同一個對話裡，AI 記得自己剛才「為什麼這樣寫」，檢查時會沿著同樣思路找支持自己的證據——它會驗證，不會證偽。就像自己改自己的考卷，錯的地方看十遍也看不出來。開新對話＝換一個沒有包袱的腦袋，只看程式和規格，這才是真正的第二雙眼睛。

Q2：為什麼 AI 不能自己宣告完工？

「看起來做完」和「真的做完」差很遠，而 AI 天生偏向前者。完工有三關：TASKS 無殘留 → Done Criteria 逐條成立 → review 全綠。三關全過，AI 也只能說「候選完工」——最後拍板的是人。這不是不信任 AI，是把「說了算」的權力留在該在的地方。

Q3：為什麼規則不全部寫進 CLAUDE.md？

CLAUDE.md 每次對話都付 token，而且規則越長，每一條被記住的機率越低。所以採「路由器」設計：常駐的只有 20 行路標，細節放在「做那件事才載入」的檔案裡。省錢，而且每條規則出場時都是主角。

七、新手上路三步

  1. 複製整個資料夾到你的專案根目錄（不要挑著複製，檔案之間有相互引用）。
  2. 填 harness/SPEC.md（照 examples/ 抄格式），導入期補 CODE-RULES-* 的公司實值。
  3. 開始：/api-loop 你的功能名——剩下的流程 AI 會照著走，該問你的時候它會用選擇題問。

有疑問先查 USER-GUIDE.md 速查表；想知道某條規則的來歷，看 docs/case-studies.md。
