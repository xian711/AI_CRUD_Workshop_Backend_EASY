AI Harness v5 使用手冊

低 token、SDD 優先的後端 API / CRUD / UI 雛形 AI 協作治具（核心不綁技術棧，預設 .NET＋Vue）

不是 AI 變聰明，而是 Harness 讓 AI 被正確約束
為什麼5 分鐘上手六條鐵律Mode 與閘門驗證分級逐檔詳解工作坊導入

為什麼需要 Harness

Model 是引擎，Harness 是流程與治具。沒有約束的 AI 會亂猜 response 格式、發明商業規則、用假資料冒充完成。

這套 Harness 用規格（SDD）、測試（TDD）、閘門（Review）限制 AI，讓它只能在可 review、可驗證、可修正的範圍內工作。AI 負責快速產生第一版（規格草稿、測試、程式草稿、UI 草稿）；工程師負責判斷商業邏輯、review 與決定是否採用。

5 分鐘上手

步驟做什麼
1把整個 aspnet-api-ai-harness-v5/ 資料夾複製到專案根目錄
2填 harness/SPEC.md（Feature＋FR / BR 編號；UI 雛形只需 Feature＋CRUD UI Spec 兩節）
3依情境執行 /api-loop、/crud-loop 或 /ui-loop
4段落完成執行 /milestone-loop（文件與 UML 圖同步、掃重構）
5完工前開新對話執行 /review-loop；❌ 修完重審通過才算 DONE

六條鐵律（每條都有「為什麼」）

  1. SDD first：規格沒有的不做，範圍外實作預設移除。為什麼：AI 會過度發揮、寫出沒人要求的功能——規格是唯一的授權來源。
  2. 誠實原則：未實作回 501 不回假資料；mock / seed 必標示；效能標 [待實機]。為什麼：AI 傾向「看起來完成」，假 200 與捏造數字比沒做更危險。
  3. 審寫分離：產碼與審查不同對話；審查者只指問題不改碼。為什麼：同一對話自審會沿用自己的推理路徑，看不見自己的盲點。
  4. 驗證自帶回圈：每個產出掛驗證；修正之後必須複驗。為什麼：靠人記得驗一定會漏，驗證必須是流程的一部分。
  5. 越權即標記：[SA 確認]、[SD 待定]、[DEV 實作]、[待實機]，不自行裁決。為什麼：AI 遇到不明處會自行腦補，標記踢回比錯誤的猜測便宜。
  6. 互動式決策：人工決策用選擇題取得答案（2–4 選項、標建議項），不只列清單。為什麼：只丟待辦清單人常不回應；給選項＋建議能立刻做決定，答案回寫 SPEC / LOOP。

三個 Mode ＋ 兩個閘門

情境Mode / 指令重點產出
後端 APIAPI　/api-loopSDD、Mock、TDD、測試草稿、OpenAPI（dev）、curl smoke ＋ .http
後端＋CRUD 畫面CRUD　/crud-loop再加 UI Spec、Design System Mapping、Page Draft、Token Check
純畫面雛形（無後端）UI　/ui-loopUI Spec、Page Draft（綁 mock、// TODO: DEV 串接）、待人工目視清單
SPEC → BUILD → MILESTONE（/milestone-loop）→ REVIEW（/review-loop，新對話）→ DONE

Milestone 閘門（段落收尾）：文件同步（程式為準，SPEC / README / UML 圖跟上）＋重構掃描（含冗餘註解清理；小改直接做並複驗、大改以選擇題問人）。為什麼：程式迭代文件必掉隊、過時的圖比沒圖更糟；重構集中處理避免每輪順手大改。

Review 閘門（審寫分離）：三維度（Completeness / Correctness / Coherence）＋雙向偵測——設計遺漏（DG）與過度設計（OE）同等重要；修正方有依據可對單一 ❌ 申辯重審（限一次）。為什麼：AI 不只會漏做，也會過度設計；審查者也會看走眼，申辯防一個誤判卡死整條線。

完工判斷（三關）：① TASKS.md 無 - [ ] 殘留 → ② SPEC Done Criteria 逐條成立 → ③ Review 無 ❌。三關過後 AI 回報「候選完工」，由人最終核可——AI 不自我宣告完工。

驗證分級（成本由低到高）

級別內容成本時機
L0build / typecheck零每次改碼後
L1自動化測試（後端走 scripts/run-tests.*、前端單元測試）低每個 loop 結尾
L2API smoke：curl.exe 實打、貼真實回應、附指令、同步 .http低中API 實作完成後必跑
L3真實瀏覽器 E2E（外部 API 一律 mock）高預設跳過，驗收才跑
為什麼分級：各級成本差距極大，永遠先跑便宜的，前一級不過就不跑下一級。誠實原則的落點：跑不起來就標 blocker，不得捏造輸出；每條指令標註成本。

模型分級（同一邏輯用在模型成本）：一般產碼 Sonnet 即可；架構變更／安全路徑、同一問題第 2 輪 fix、/review-loop 時 AI 會提醒你 /model 升 Opus——提醒不阻塞，錢花在判斷力值錢的地方。

逐檔詳解：每個檔案的內容與為何要設定

四層原則：HARNESS＝規則、commands＝動作、modules＝細節、docs＝參考——每條規則只寫一處，其餘引用，避免規則漂移。

檔案內容為何要設定
commands/api-loop.mdAPI 固定流程：SPEC 併入 → 產出（引用編號；TDD 先自列清單再看既有測試——防錨定）→ 輸出前四檢查 → L0/L1 → L2 smoke → 對照事件表回填 LESSONS；架構／安全任務與第 2 輪 fix 提醒升 Opus一句指令觸發固定流程，避免每次 prompt 品質不一；四檢查放輸出前，便宜的自我把關先於昂貴驗證
commands/crud-loop.mdAPI 流程＋UI Spec 先行、Token Check、缺件超過 3 個以選擇題熔斷畫面返工成本高，先審 UI Spec 再產碼；批量建元件需要人先點頭
commands/ui-loop.md雛形流程：UI Spec → Page Draft（綁 mock、標 // TODO: DEV 串接）→ Token Check → 人工目視無後端情境走 crud-loop 會產生多餘產物；美學判斷 AI 不可靠，標「待人工目視」
commands/milestone-loop.md段落收尾：文件同步、UML 圖更新、重構掃描＋冗餘註解清理（功能型指令前後計數防誤刪；小改直做並複驗、大改選擇題問人）程式迭代文件必掉隊；重構與註解衛生集中在收尾處理
commands/review-loop.md審查閘門：三維度＋雙向偵測、FR 覆蓋矩陣、❌/⚠️/💡 分級與降級、申辯重審（附依據、每條限一次）；建議以 Opus 執行必須新對話執行（鐵律 3）；覆蓋矩陣抓漏做、OE 清單抓過度設計、申辯防誤判卡線
skills/aspnet-api-crud-sdd-loop/Mode 判斷與觸發、四條禁止使用者忘記打指令時，AI 仍自動遵循流程
skills/gis-frontend/GIS 前端角色：地圖規則與實戰坑，疊加在 crud / ui loop 之上skill 描述常駐一行、本文觸發才載入——專業領域規則零常駐成本
hooks/session-start.sh＋settings.jsonSessionStart hook：開新對話／compact 後自動注入 Harness 提要（鐵律、路由、模型分級、完工三關、底線）長對話後早期規則會被壓縮或淡出；hook 讓規則自動重灌，不靠 AI 記得。第一次啟動會詢問是否信任，同意即可

harness/（每次任務的工作檔）

檔案內容為何要設定
SPEC.md規格範本：FR / BR / TC 編號、交接標記、API contract、Mermaid 圖、Done Criteria編號讓審查能產覆蓋矩陣、抓孤立設計；Done Criteria 讓「完成」可判定
TASKS.md任務分解（WBS）：checkbox 條列，每條標對應 FR 與驗證方式；驗證通過才勾；commit（由人主導）時勾選與產出放同一個- [ ] 機器可掃，review 一行判斷做完沒；TASKS＝進度快照、git＝完成證據、LOOP＝只記活待辦
CODE-RULES-api.md後端規範：C# 分層命名、API envelope、表命名 / 審計欄位 / migration；附範本清單AI 不會自動符合公司慣例；按面向拆檔，純 UI 工作不載入後端規則
CODE-RULES-ui.md前端規範：Vue 慣例、API 封裝、env、格式化；附範本清單同上——純後端工作不載入前端規則
LESSONS.md錯誤防範庫：問題 → 原因 → 防範；回填時機是五項事件表 E1–E5，loop 結尾逐項對照同樣的坑 AI 會重複踩，防範要寫成「開工前必掃」的清單；記不記用機械對照，不靠自由心證
LOOP.mdloop 狀態：Gate、待辦、本輪決策——只記待辦不記已完成記已完成會吃掉上下文，還誘導 AI 自我滿足；階段完成不自行推測下一階段

三堂工作坊（各 2 小時）

堂次主題亮點演練
①API Mode：查詢派工單清單 API無 Harness vs 有 Harness 對比；誠實原則（故意留未實作端點）；L2 smoke 實打
②CRUD Mode：設備資料維護UI Spec 先行；Token 檢查閉環（故意塞硬編碼色值看它收斂）；雛形情境改用 /ui-loop
③Review Gate＋段落收尾新對話審查、修 ❌ 重審；/milestone-loop 文件與 UML 圖同步；L3 瀏覽器驗收；導入討論

導入節奏

階段做法
第一週每人選熟悉 API 跑 API Mode（不要求 merge）
第二週低風險 CRUD 或 UI 雛形，review 是否符合 Design System
第一個月補齊 CODE-RULES、Design System 摘要、error code 表
第二～三個月常見 pattern 入 Harness、累積 LESSONS、/review-loop 納入 code review、真實小功能試導入
帶回去的三句話：規格沒有的不做；做不到的誠實說；審查的人不寫碼。
