# 接手既有系統盤點範本（intake-checklist）

接手不是自己從零寫的系統時，**先盤點、再開發**。流程：收料 → 知識盤點 → 放行判斷，之後才走對應 loop。

## 1. 收料清單

向系統負責人（或前手）收集下列材料。**P0＝沒有就不能開工；P1＝可先開工、開工後補**。

| # | 項目 | 要收什麼 | 優先 |
|---|---|---|---|
| 1 | 系統定位 | 一段話：這系統給誰用、解決什麼問題、目前維運狀態 | P0 |
| 2 | 程式倉庫清單 | 前端、後端、批次、共用套件——**凡是前端會呼叫、批次會存取的服務都要列**，不要只給主倉庫 | P0 |
| 3 | 真實工作流程 | 使用者實際在做的 3–5 條操作流程（角色 → 操作 → 結果） | P0 |
| 4 | 資料資產 | DB 連線（唯讀即可）、主要資料表 / View / Stored Procedure 清單 | P0 |
| 5 | 環境與部署 | 各環境 URL、設定檔位置、部署方式、出問題找誰（窗口） | P1 |
| 6 | 範例輸出入 | 主要 API 的真實 request / response 各一份（去識別化） | P1 |

## 2. 知識盤點表

開工前把每個面向的掌握程度標成四狀態，**證據力由高到低：實庫查詢 > 原始碼 > 既有文件 > 口頭轉述**；只有口頭或文件佐證的，最多標「部分」，不得標「已驗證」。

| 狀態 | 意思 |
|---|---|
| 已驗證 | 有實庫查詢或原始碼佐證 |
| 部分 | 有線索但沒完整看過（只有文件或口頭） |
| 缺失 | 完全沒有材料 |
| 衝突 | 兩個來源說法不一致（例如文件說 A、程式碼是 B） |

| 面向 | 狀態 | 證據來源 | 備註 |
|---|---|---|---|
| 系統定位與使用者 | | | |
| 後端架構與分層 | | | |
| API contract（envelope、錯誤格式） | | | |
| 資料模型（表 / View / SP） | | | |
| 前端結構與呼叫方式 | | | |
| 環境與部署 | | | |

## 3. 放行判斷

| 盤點結果 | 判斷 | 下一步 |
|---|---|---|
| 涉及面向全部「已驗證」 | 可直接開工 | 走對應 loop（`/api-loop` 等） |
| 有「部分」但無「缺失 / 衝突」 | 可開工，須聲明前提 | 每條前提記成 Assumption 並寫驗證方式，開工後儘早驗 |
| 涉及面向有「缺失」或「衝突」 | 需先補料 | 依鐵律 6 用選擇題向人要 P0 項目，補齊後重盤 |

規則：

- 只盤**本次任務涉及**的面向，不為盤點而盤點。
- 有「缺失 / 衝突」時，分析與結論必須註明「基於不完整資訊」，不得以完整因果鏈的口吻下結論。
- 「衝突」一律以實庫或原始碼為準，並回頭修正文件（記入 milestone 待辦）。
