① 請求的一生

你在瀏覽器按一下「儲存」，資料怎麼一路跑到 PostgreSQL 再回來？跟著箭頭走一遍。

白話重點
  • 前後端分離：前端（Nuxt）和後端 API（.NET）是兩個各自啟動的程式。圖上的 Controller、Service、EF Core 三格合起來，就是後端 API；它們都在 5080 這一個程式裡。像餐廳：前端是外場，API 是廚房，外場只能從出菜口（HTTP）把點單遞進廚房。
  • 開發期瀏覽器不直接打後端，而是先到 Nuxt（3100），由 devProxy 同源轉發到 API（5080）——所以本版後端還沒設定 CORS 也能動。
  • 去程（紅）是「請求往右送」，回程（綠）是「資料往左回」。每一層只做自己該做的事，這就是「分層」。
  • 前端只要把記憶體 mock 換成打這支 API，這條動線就通了——資料從此存進資料庫，F5 也不會消失。

② 分層架構

依賴方向單向向右：Controller → IMemberService → MemberService → AppDbContext → PostgreSQL。上層只依賴下層的介面。

白話重點
  • 「Controller 薄委派」是可檢查的紀律：看它有沒有 if／查詢／組字串，有就是違規。
  • 介面 IMemberService 的價值在於可替換、可測試，不是為了多一層而多一層。
  • D11 是本範本刻意偏離原單位範本「全包 try/catch」的地方——全包會把基礎設施故障誤報成業務 404。

③ POST 循序：新增一筆的完整步驟

從請求進來到回 201，中間發生什麼：驗證分支、SEQUENCE 取號、Mapperly 映射、SaveChanges；含未預期例外 → 500 支線。

白話重點
  • SEQUENCE「唯一但允許缺號」：rollback／失敗／快取都會消耗號碼且不退回，所以號碼可能跳號——但保證不重複。這比前端「掃最大值+1」穩，不會兩個請求搶同一個 id。
  • 驗證失敗（②③）發生在框架模型繫結階段，根本不會進 Service——這是為何驗 400 的測試不用真的碰資料庫。
  • id 和 updatedAt 都是後端在這裡自己產的，前端 body 就算帶了也會被忽略（防竄改）。

④ DB 綱要

template_member 表（snake_case 欄位、四組 CHECK、qualifications 原生陣列、bloodType 選填）；SEQUENCE 從 25 承接 24 筆種子；camelCase↔snake_case 對照。

白話重點
  • 四組 CHECK 的允許值由程式的 MemberEnums 常數組出，跟 DTO 的 [AllowedValues] 共用同一份字面值——改一處兩邊同步，不會漂移。
  • qualifications 用 PostgreSQL 原生陣列 text[]，免另建關聯表；bloodType 是選填，DB 為 text NULL，沒填就是 NULL、CHECK 自然放行。
  • 用 psql 下 SELECT 看到的是 snake_case 欄位；API 對外才是 camelCase——這正是「JSON camelCase / DB snake_case」這條契約的實體證據（psql 三招見 PSQL_QUICKSTART.md）。

單元（不碰 DB，快）在底、整合（打測試庫）在中、手動與 E2E 在頂。基準 49 條，dotnet test 全綠。

白話重點
  • 本範本整合測試占比偏高（18 條／49 條）——因為 CRUD 商業邏輯薄，驗證多靠 DataAnnotations 宣告式完成，真正要單元測試蓋的「手寫邏輯」有限。這是值得課堂討論的點。
  • 測試庫固定叫 ai_crud_template_test，且 EnsureDeleted 前防呆「DB 名必須 _test 結尾」——避免誤刪開發／正式資料庫。
  • 斷言紀律：清單斷「至少 24 筆」不斷「恰 24 筆」、POST 斷 id 格式不斷固定 M-025——讓測試不因執行順序而假紅假綠。
